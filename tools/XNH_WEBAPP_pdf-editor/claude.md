## 技術選定理由

### pdf.js（pdfjs-dist）を選んだ理由

- Mozillaが開発・維持する実績のあるOSSライブラリ
- ブラウザ完結で動作する（Node.js不要）
- PDF仕様のほとんどをカバーしており、レンダリング品質が高い
- CDN不要（npmでバンドル可能）
- ライセンス: Apache 2.0

### pdf-lib を選んだ理由

- 純粋なTypeScript/JavaScriptで書かれており、ブラウザ内で完結する
- PDFページの作成・操作・注釈追加・保存が可能
- pdf-lib は既存PDFへの注釈追加も対応
- ライセンス: MIT
- 代替候補の jsPDF はPDF生成が主目的で既存PDF読み込みが弱い
- 代替候補の PDFKit はNode.js向けで、ブラウザ対応が不完全

### React を選んだ理由

- コンポーネント分割による保守性
- Zustandとの親和性
- TypeScriptサポートが充実
- 代替のVue.jsも同程度だが、Reactの方がエコシステムが広い
- Vanilla JSは複雑なUI状態管理が困難

### Zustand を選んだ理由

- 軽量（5KB未満）
- Reduxに比べてボイラープレートが少ない
- React外からも状態を操作しやすい（pdfjs-distとの連携で重要）

### Vite を選んだ理由

- 高速な開発サーバー・HMR
- ビルド設定がシンプル
- TypeScript対応が標準
- webpack より設定が少なく保守しやすい

## 問題点・既知の制約

### pdf-lib の注釈互換性

- pdf-lib で追加したFreeText注釈は、一部のPDFビューアで表示されないことがある
- 特にiOS Safari内蔵ビューアでの表示は未検証
- Acrobat Reader（デスクトップ）での動作確認を基本とする

### フラット化の難しさ

- 注釈をページ内容（コンテンツストリーム）に焼き込む処理はpdf-libだけでは完全に実現が難しい
- pdf-libのページ描画API + canvas描画を組み合わせる方法を検討中
- 初期フェーズでは「標準PDF保存（注釈オブジェクト保持）」のみとする

### Worker の設定

- pdfjs-dist を npm でバンドルする際、Worker ファイルのパス設定が必要
- Vite では `?url` インポートで対応する
- 環境によってWorkerが正しく起動しない場合がある（要テスト）

### 大容量PDF

- 複数の高解像度ページがある場合、canvas への描画でメモリを多く消費する
- ページのLazy Loadingで対処予定（サムネイルは縮小レンダリング）

## 判断保留事項

### ハイライト注釈の実装方式

- **方式A**: テキスト選択ベース（pdf.jsのテキストレイヤーを使い、選択範囲を取得して注釈化）
  - Pros: 正確な位置・Acrobat互換
  - Cons: テキストレイヤーの座標変換が複雑、フォント依存
- **方式B**: 矩形ベースの擬似ハイライト（ユーザーが矩形を描いてHighlight扱い）
  - Pros: 実装シンプル
  - Cons: テキストとの対応が取れず、Acrobatの真のHighlightとは異なる
- **現在の判断**: フェーズ2で方式Aを試みる。難しければ方式Bを代替として明示する

### フラット化PDF

- pdf-lib のみでのフラット化は難しい可能性が高い
- 将来的には Puppeteer / headless Chrome を使ったサーバー側処理も検討
  - ただしそれはローカル処理方針と相反するため、オプション扱い
- 現時点は「フラット化は配布用にcanvas描画した画像PDFを生成する」方式を仮置き

### OCR テキストレイヤーの追加（Phase 5 調査メモ）

- **目的**: スキャン PDF や画像のみのページに対しても文字検索・本文編集を可能にする
- **候補ライブラリ**:
  - Tesseract.js: 完全ブラウザ動作、日本語含む多言語対応、ライセンス Apache 2.0
    - Pros: ローカル処理方針に合致。Web Worker 対応で UI ブロックを避けられる
    - Cons: 言語データ（trained data）が大きい（日本語: 10〜15MB）、初回ダウンロード必要
    - 精度は印刷品質に依存。手書き・複雑なレイアウトは苦手
  - PaddleOCR (paddle.js): 軽量だが日本語サポートが弱い
- **検討した実装方針**:
  1. ユーザーが対象ページを選んで OCR 実行 → 認識結果を `S.textItems[pageId]` に注入し、`textedit` ツールと検索インデックスに乗せる
  2. 認識結果を不可視テキストレイヤーとして PDF に書き戻す（pdf-lib で透明色のテキストを描画）
- **判断**: Phase 5 では実装見送り。Tesseract.js を将来取り込む際は Phase 5.5 として「OCR ボタンで現在ページ / 全ページを OCR → textItems 更新」を最小版として追加する想定。trained data のホスティング場所（同梱 vs CDN）は別途検討
- **既知の難点**: OCR 結果の rect は文字行単位で粗いため、`textedit` の `sourceId` 紐付けは大雑把な近似で割り切る必要がある
